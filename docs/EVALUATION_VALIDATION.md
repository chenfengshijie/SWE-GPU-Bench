# Campaign validation: 2026-11-06 UTC

The portable campaign implementation passed **449 CPU tests and 3 subtests**,
including the existing collection tests. A Python 3.12 environment installed the
built wheel outside the checkout, loaded all 39 parser recipes and packaged
resources, and prepared/verified all four task combinations through the installed
CLI. Both wheel and source distribution built successfully.

## H100 smoke evidence

The [selected evidence](evidence/evaluation-smoke-20261106.json) covers
`NVIDIA__cuda-python__1221`, base commit
`3dcdd6d46eedc07761d4a8a3375d497fe0c5248d`, using its separate correctness and
performance records. Each task used one NVIDIA H100 80GB, CUDA toolkit 12.8 and
driver 535.161.08. All profiles used `high` reasoning effort. The total number of
concurrent jobs stayed at or below two, with a 7,200-second case deadline.

| Task | Mode / model | Recorded outcome |
|---|---|---|
| Correctness | Oracle / GPT-6.1 | Passed: 2 tests |
| Correctness | Agent / GPT-6.1 with Codex | Passed: 2 tests |
| Performance | Agent / DeepSeek-V4.1-Flash with OpenCode | Correctness passed: 1 test; measured improvement 42.3861% |
| Performance | Oracle / DeepSeek-V4.1-Flash | `model_output_error`: empty final answer; no candidate or performance conclusion |

The performance Oracle made one model request. Reported usage was 16,384 output
tokens, all classified as reasoning tokens, exhausting the configured output
budget without a final answer. The JSON edit parser rejected the empty answer. No
answer was regenerated. Candidate validation and numeric comparison were not
reached for this task.

The other three tasks reused answers generated by real model calls in earlier
development snapshots. Their candidate manifests, patch hashes and model-output
hashes trace those origins. The final runner performed fresh validation; the
performance Agent baseline and candidate were measured again. All four final
attempts used the same 63 packaged source/resource files, identified by the public
code digest in the evidence. Revalidation does not imply a new model generation.

An earlier performance Oracle attempt timed out while downloading repository
history, before a model call. Its infrastructure result remains preserved. The
replacement was submitted only after confirmed termination and used the pinned
base-only fetch. The timeout is separate from the model-output failure above.

Every final attempt passed the filesystem/CUDA preflight, including native device
allocation, fill and copy in both a process and its child. These jobs used the
public External adapter protocol with a separately maintained deployment adapter.
Docker launch/recovery behavior has CPU contract tests; an actual Docker launch
was not exercised on the development host.

## Scope and reproducibility

The measured percentage uses the recipe's lower-is-better formula. It is one
smoke workload and makes no statistical significance claim. All 39 performance
parsers have explicitly synthetic fixtures; the other 38 recipes were not run on
GPU as part of this smoke.

The evidence exports selected fields and hashes. Original configurations,
receipts, logs, responses and candidate patches remain in their local run
directories. Deployment identifiers and credentials are not part of the public
report. `public_code_sha256` hashes the sorted, compact JSON mapping of frozen
`code/` paths to their SHA256 hashes, excluding runtime configuration and the
deployment adapter. It is distinct from the final Git commit/tree hash.

See [campaign setup and recovery](EVALUATION_CAMPAIGNS.md) and the
[external adapter protocol](EVALUATION_ADAPTERS.md) to reproduce the workflow in a
compatible environment with explicitly selected records and model profiles.
